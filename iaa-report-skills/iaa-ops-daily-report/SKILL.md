# IAA 运营日常汇报（三段式）

把一天的 IAA 投放操作 + 流水变化，整理成给小迪看的**三段式汇报**（**当前情况分析〔含操作明细〕→ 处理思路 → 当前进展**），确认后发到指定飞书任务作为评论。操作关键点不单独成段，并入「当前情况分析」里的 `【操作】` 块。

## 何时用 / 何时不用
- ✅ 小迪说"跑下运营日常汇报（日报/周报）""整理下今天/这周的操作"。
- ❌ 只要数据看板/HTML/推群的 → 那是 `iaa-daily-report`（生产日报），不是这里。

## 流程（每次严格按序，不可跳步）

```
1. 拉数据      scripts/fetch_data.py  →  4 路源文件（见 §数据源）
2. 算操作(打底) scripts/build_report.py --day {昨日} [--prev {前日}] --indir /tmp/ops --json /tmp/ops/ops_report.json
                → 新/停/加/减候选清单(按实际转化数) + 每 offer 转化/流水影响 + 包级 Top；再叠第 3 步群修正
3. 读群补原因  lark-im 拉运营群当日消息 →  给每个操作找根因；群里没写清的标"原因待确认"
4. 套模板      references/report_template.md →  填三段（情况分析含【大盘】/【操作】两块），产出草稿
5. 给小迪确认  把草稿 + 关键数字口径发小迪，等点头
6. 发任务评论  lark-task 以 --as user 把定稿发为任务评论
```

**第 3、5 步是这个 skill 的灵魂，不能省。** 操作"原因"大量来自运营群自由播报，数据里查不到；数字口径要跟小迪对齐后才发（见 §口径）。

## 字段口径（已实测，勿再猜；2026-09 由 cap 口径整体切到「实际转化」口径）
- **实际转化数** = 回调 `wm_all_callback` 中满足 **`channel=='4580' 且 event_name 为空 且 blocked_sub_reason 为空`** 的行数（对齐生产日报 `daily_report_new_api.js` 的 `tran_num`）。游戏内事件（upgrade_station/session/Ad_Watched…）、被拒(blocked) **都不算转化**，别用全行数当转化。
- **转化流水** = 上述转化行的 **`payout`** 求和（不是 `self_payout`）。按 `(offer_id, come_from)`、`utcdate` 归日。
- **头条总流水** = 自有转化行 `payout` + 外部 `iaa_call`/`iaasdklab_call` `payout`（外部按 **clickid 去重**）。自算与早会/日报仍有 ±几十刀差 → 第 5 步核对。实测 9.22 自算 $6,900.24 vs 人肉报告 $6,901.44（差 <2 刀，此 payout+转化行口径明显优于旧 self_payout 口径）。
- **客户/广告主** = `come_from`（回调）≈ `ad_user`（任务）；**包** = `package_name`；**offer** = `offer_id`。转化分类只用回调，不再 join 排班任务（cap 口径已弃）。
- 金额字段含脏值（如字面量 `{payout}`），**必须用 try/float 容错解析，跳过非数值行**（详见全局 CLAUDE.md 音频脚本同类坑）。

## 操作分类口径 —— 已锁定（2026-09 多轮与小迪对齐，整段切到「实际转化」口径）

**演进（勿再走回头路）**：① 最初按排班目标 `cap` diff 分类 → 出现"目标加了、当天实际转化/流水反而跌"被读成矛盾（tictactoe +50cap/−$35）；② 小迪拍板：**新/停/加/减全部按「实际转化数」判，不再用 cap**。好处：加量=转化真涨（流水自然正），cap 加了但没兑现的会正确归到减量，从根上消掉"加量却流水降"的歧义。仍属**混合口径：数据打底 + 群修正**（人肉计数无法纯数据复现，见 §实测）。

**build_report.py 已实现规则（改前须重新对齐）：**
| 维度 | 口径 |
|---|---|
| 判定基准 | **实际转化数**（见 §字段口径的转化判据），**不用 cap** |
| 操作粒度键 | `(offer_id, come_from)`：每家客户 offer 一般独立；两家撞同 offer_id **各算一条**（新/停/加/减同规则） |
| 一次操作门槛 | `|Δ转化数| ≥ 10` |
| 新单 / 停单 | 一侧转化==0、另一侧 ≥10 |
| 加量 / 减量 | 两侧都 >0 且 Δ ≥ +10 / ≤ −10 |
| 流水影响 | 该类 offer 转化行 `payout` 的日环比（独立于转化升降分开读） |

**报告展示规则（小迪定，详见 `references/report_template.md` 顶部"核心展示规则"）**：广告主永远第一；offer/包仅在其流水影响 **≥ $15** 或该包为全类主线时才点名，否则只报客户总额；转化数每类只标一次；数字带单位且用 `、·（）` 隔开不裸挤；多家撞同包合并一句；「当前情况分析」内分 `【大盘】`/`【操作】` 两块、每行带前缀标签（流水/指标/概览/原因/口径）；后两段 处理思路 / 当前进展 用 1/2/3/4 编号。

**分工（关键）**：build_report.py 只出**可核对的客观变动候选清单**（"打底"）；第 3 步 LLM **读运营群** 把每类计数修到运营口径、补根因，冲突时**以群播报为准并标注来源**。逐类计数与人肉数有差属正常（净影响、焦点包、客户应基本对得上）。

**总流水（头条）口径**：自有转化行 `payout` + 外部 `payout`（clickid 去重）自算并**标 `headline_source`**；因归日/去重细节，与日报头条仍 ±几十刀差，**发布前必在第 5 步与小迪/早会核对**。日报不落可查历史，故不自动读 card。

## 日 / 周两种模式
- **日报**：`fetch_data --start 前一日 --end 昨日` → `build_report.py --day 昨日`，diff 昨日 vs 前一日（单日转化）。
- **周报**（触发词"**整理下 iaa 业务周度评论**"）：`weekly_roll.py --end {本周周日} --threshold 10`，**全量按日均**——每个 `(offer,come_from)` 7 天求和 ÷7 = 日均，与上周日均做差，**分类/流水/转化都是日均口径，门槛沿用日报 ±10（不自造周门槛）**。受众是老板 / 业务推进评论，比日报更收敛：〔操作〕只点名影响最大的头部广告主、其余归"多家"、影响大的包单独点出（规则见 `references/report_template.md` §周报专属规则 W1–W6）。定稿模板见该文件"周报填充示例（9.21–9.27·定稿）"。
- 历史源数据时间分割沿用生产口径：17:00 前用实时预估、17:00 后用结算（见全局 CLAUDE.md #4），但**运营汇报通常 T+1 跑昨日全天结算数据**，一般不涉及当日预估。

## 已知坑（沿用全局 CLAUDE.md）
- 金额字段（`payout`/`self_payout`）含脏值 `{payout}`，务必 try/float 容错，跳过非数值行。
- **转化 ≠ 回调行数**：一条回调算转化须 `channel=4580 且 event_name 空 且 未 blocked`。直接数全部行会把游戏内事件(upgrade_station/session/Ad_Watched…)和被拒算进去，虚高 ~1.6 倍（17033 行 → 10473 转化）。
- 转化流水用 **`payout`**（对齐生产 CPI），不要用 `self_payout`（旧口径，与运营认知差更大）。
- `wm_iaasdk_task` 每 offer 一天多条任务，cap **取 max 不取 sum**（cap 口径已弃，仅交叉核对时用）。
